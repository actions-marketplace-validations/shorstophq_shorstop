# Contributing to ShorStop

Thanks for helping. Bug reports, missed detections, new rules and fixes are
all welcome.

For a **security vulnerability in ShorStop itself**, don't open an issue:
follow [SECURITY.md](SECURITY.md).

## Before you start

- **Small fixes and new rules:** open a pull request directly.
- **New detectors, new output formats, new flags or changed severities:** open
  an issue first, so we can agree on the approach before you write the code.
- **A missed detection or a false positive:** open an issue with the
  smallest snippet that shows it, the rule ID if there is one, and the output
  of `shorstop version`.

## Setting up

You need Go 1.27 or later, and for linting
[golangci-lint](https://golangci-lint.run/) v2.15.0 (the version CI pins).

```sh
git clone https://github.com/shorstophq/shorstop
cd shorstop
make test    # go vet + go test -race
make lint    # golangci-lint
make build   # bin/shorstop
```

`make fuzz` runs every fuzz target for 30 s each (`FUZZTIME=5m make fuzz`
for longer). `make release-snapshot` builds every release archive locally if
you've changed `.goreleaser.yaml`.

## Adding a rule

Built-in rules live in [`internal/rules/rules.yaml`](internal/rules/rules.yaml);
the format is documented on `type Rule` in `internal/rules/rules.go`.

- **Rule IDs are permanent.** They appear in reports, baselines and
  `shorstop:ignore` comments, so never rename or reuse one. To replace a rule,
  retire it and add a new ID.
- **Regex rules need `examples`**, and every example must match the pattern.
  The loader rejects the rule otherwise, so the examples double as tests.
- **Add a fixture** under `testdata/fixtures/<language>/` that the rule
  finds, then regenerate the golden output for that detector and review the
  diff:

  ```sh
  go test ./internal/detect/regex -update
  git diff testdata/
  ```

  The goast, cert, config, deps and regex detectors and the CBOM report all
  take `-update`.

## Pull requests

- **`make test` and `make lint` must pass.** CI also runs every fuzz target,
  builds every release platform, and tests the GitHub Action on Linux, macOS
  and Windows.
- **Output must be deterministic.** The same input has to produce
  byte-identical reports, since users diff them and commit baselines. Sort
  with a full tie-break, not just the obvious key.
- **Explain non-obvious decisions in
  [`docs/decisions.md`](docs/decisions.md).** Each function that makes a
  design choice has an entry there: what it does, the alternatives, and why
  this one. Update the entry when you change the behaviour.
- **Keep dependencies minimal.** ShorStop has four runtime dependencies.
  Adding one needs a reason in the pull request.
- **Write commit messages as plain sentences** that say what changed, like the
  existing history (`Make scan output order deterministic`).
- **Don't commit real secrets.** The keys and certificates under `testdata/`
  are throwaway fixtures, generated by the scripts beside them.
